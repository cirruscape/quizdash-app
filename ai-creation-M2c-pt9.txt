------------------------------------------------------------------------------

USER:

[The developer had redeployed the bootstrap stack and pushed. The

CLAUDE:
1. How the screens stay in sync. ADR 0002 says events can be lost, and
   snapshots are the truth. The simplest approach that's robust by
   construction is to render every screen from the snapshot only. A pushed
   event never updates the screen directly. It just says "something
   changed", and the client re-fetches its snapshot. A slow poll catches
   anything lost. The cost is about 100-300 ms of extra delay per update.
2. Host sign-in: Amplify's ready-made Authenticator, styled to match.
3. What to test:
     W1 the sync controller (pure TypeScript): when to re-fetch, and the
        countdown corrected for clock differences
     W2 a new GET /api/quizzes route, test-first through S1-S3
   The screens themselves checked by hand in dev on a phone and a laptop.
4. Plain CSS, designed for phones first; a join link (/play?code=ABC234),
   no QR code for now.

USER:
yes, go with 1–4 as recommended

3. W1: THE SYNC CONTROLLER
------------------------------------------------------------------------------

[Claude wrote the sync controller test-first, with fake timers and a fake
 server whose responses the test releases one at a time:]
    - fetch on start
    - on events: re-fetch, folding a burst of events into exactly one
      follow-up fetch
    - ignore events for versions already seen, and stale responses
    - poll when no events arrive, recovering a lost one
    - re-fetch just after a deadline, on the server's clock, even with
      the device's clock 10 seconds off
    - keep going after a failed fetch
    - do nothing once stopped
    - a countdown function on the server's clock, never negative

[Claude also tidied its own test helper, which had relied on obscure
 "var" hoisting.]

4. THE SCREENS
------------------------------------------------------------------------------

[Plumbing: runtime config loaded from /config.json; an API client with
 plain-language error messages; a browser AppSync Events client that
 reports only event versions and reconnects with backoff; and a React hook
 combining the snapshot sync with real-time signals.]

[Player screens:
   - Join: the code can come from a join link, with a "return to your
     game" banner
   - Lobby, Question (big coloured Option tiles, a countdown, "answer
     locked in"), Reveal (the correct Option, your points and rank),
     Finished (the final Leaderboard)
   - a "you were removed" screen, and silent rejoin on reload ]
[Host screens:
   - Amplify sign-in and sign-up
   - Home: resume a Game in progress, or start one from a Ready Quiz
   - Lobby: a big Join Code, the join link, the Players with Remove
   - Question: a countdown and "N of M answered". When the countdown
     reaches zero, the Host's screen asks the server to close the
     Question, retrying every second until it's closed (ADR 0003)
   - Reveal: per-Option counts and the Leaderboard, then Next or Finish ]

[Claude caught two problems in its own code before running anything: an
 unused helper left in the deadline-close effect, and a real race in it
 (if the screen changed before the token arrived, a timer would leak).
 It rewrote the effect with a cancellation flag.]

[The first build warned that the bundle was over 500 KB, mostly Amplify's
 sign-in UI. Players never sign in, so Claude lazy-loaded the whole Host
 area, then moved Amplify's configuration into it too. A Player's phone
 now downloads about 88 KB gzipped.]

[Claude found a peer-dependency warning (Amplify UI's xstate dependency
 declares React up to 18), judged it acceptable because Amplify UI itself
 supports React 19, and flagged it for the hand test.]

5. THE WEB STACK AND PIPELINE
------------------------------------------------------------------------------

[Claude wrote infra/web.yaml:
   - a private S3 bucket, readable only by CloudFront
   - /api/* routed to the HTTP API (same origin, uncached, forwarding the
     Authorization header)
   - /config.json never cached
   - a CloudFront Function serving index.html for app routes. Claude
     chose this over CloudFront's custom error pages, because those would
     also have turned the API's real 404 responses into HTML. ]
[The pipeline's new web job builds the app, deploys the stack, writes
 config.json from the stacks' outputs (so one build serves every
 environment), uploads content-hashed assets with long caching and
 index.html and config.json with none, and invalidates.]
[Claude checked that the deploy role already had the needed permissions,
 so no bootstrap redeploy was needed this time.]

Observations worth blogging about:
  - The UI design came straight from a failure the smoke test found: since
    real-time events can be lost, the screens render only from snapshots,
    which makes them correct by construction.
  - The tricky client logic (re-fetch timing, clock offsets) was pulled
    out of React into a pure module, so it could be tested exhaustively
    with fake timers.
  - Claude looked at the build's output, not just at whether it built, and
    cut what Players' phones download by about 80%.
  - Claude was explicit about what remained unverified (the screens, the
    browser WebSocket client, Amplify with React 19) rather than calling
    M2c done.
