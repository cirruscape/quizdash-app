5. SWITCHING TO AMAZON NOVA 2, CONVERSE-ONLY
------------------------------------------------------------------------------

USER:
To resolve the anthropic model access temporarily, amend the app to instead
use Amazon Nova 2 for now. Ensure that models are always called via
Bedrock Converse API for easy swapping later

[Claude researched before changing anything:
   - AWS's Nova 2 Lite model card: the ID is amazon.nova-2-lite-v1:0. From
     ap-southeast-2 it is reachable only through the GLOBAL profile,
     global.amazon.nova-2-lite-v1:0; there is no au. or apac. profile. It
     supports Converse but not Bedrock's native structured outputs.
   - AWS's IAM requirements for global profiles: a three-part policy that
     includes a region-less foundation-model ARN.
   - Strands' compiled source: BedrockModel calls only ConverseCommand or
     ConverseStreamCommand, never InvokeModel. ]

[Claude wrote packages/agent/src/model.ts, the single place a model is
 constructed. The model ID comes from MODEL_ID, and the agent refuses to
 start without it rather than quietly falling back to a default model.]

[Claude added ESLint rules that reject InvokeModel commands, Strands'
 non-Bedrock model providers, and constructing a BedrockModel outside
 model.ts. It proved the rules work with a throwaway file containing all
 three: each was flagged, and the real code linted clean.]

[Claude made infra/agent.yaml's IAM policy driven by ModelId and
 FoundationModelId parameters, defaulting to Nova 2 Lite. It works for both
 geographic profiles (like au.) and global profiles, so switching back to
 Opus 5.5 is a parameter change. (Section 8 shows why using parameters
 turned out to be a mistake.)]

[Claude wrote ADR 0005, "Models are called only through the Bedrock
 Converse API, and chosen by configuration". It records the trade-offs:
 only portable settings, no provider-specific structured outputs, and
 global routing while on Nova. Claude also updated ADR 0001, the PRD, the
 plan and the README.]

8. THE NOVA SMOKE TEST FAILS, AND CLAUDE FINDS ITS OWN BUG
------------------------------------------------------------------------------

USER:
Smoke test A failed again, with error: aws: [ERROR]: An error occurred
(RuntimeClientError) when calling the InvokeAgentRuntime operation:
Received error (500) from runtime. Please check your CloudWatch logs for
more information.

[Claude read the agent's CloudWatch logs again. The newest failure was
 surprising: the agent was still calling Claude Opus 5.5, not Nova.]

  not authorized to perform: bedrock:InvokeModelWithResponseStream on
  resource: ...foundation-model/anthropic.claude-opus-5-5

[Claude suspected its own design. "aws cloudformation deploy" keeps a
 stack parameter's previous value unless the command overrides it, and the
 pipeline only passes Env and ImageTag. It read the deployed stack's
 parameters, read-only, and confirmed the split:
   ModelId            = au.anthropic.claude-opus-5-5   (kept from the
                                                        first deploy)
   FoundationModelId  = amazon.nova-2-lite-v1:0        (new, so it took
                                                        its default)
 So the agent asked for Opus, while IAM allowed only Nova.]

CLAUDE:
Confirmed. A parameter default only applies the first time a stack is
created. Changing it later never reaches a stack that already exists. So
"change the default and push" was wrong advice on my part. The model swap
I documented wouldn't actually have worked.

[Claude moved the model out of stack parameters and into a CloudFormation
 Mappings table in infra/agent.yaml, with one row per environment (dev and
 prod, both Nova 2 Lite for now). The IAM policy and MODEL_ID both read
 from it. Editing the table changes the template itself, so every deploy
 applies it. It also lets dev and prod use different models.]
[Claude checked the change with cfn-lint, and with CloudFormation's
 read-only validate-template, which confirmed the only parameters left
 are Env and ImageTag.]
[Claude corrected the README, ADR 0005 (which now records this incident as
 the reason for the design), the plan, and its own memory note. The new
 instructions warn never to put the model back into stack parameters.]

USER:
ALso update ai-creation-pt4-nova.txt to reflect this change if in scope,
then commit

[Claude added this section, updated the summary below, and committed.]

Lesson for the blog: Claude's first Nova design passed every local check
and still failed in production, because of how CloudFormation treats
parameters on update. Claude traced the failure to its own earlier

pipeline, and corrected the documentation that had repeated the mistake.

Observations worth blogging about:
  - Claude debugged a cloud auth failure from both ends, the AWS trust
    policy and GitHub's OIDC settings, and found a recent GitHub change
    (immutable subjects) that a stale mental model would have missed.
  - When documentation ran out, Claude chose to make the system report the
    real value (a claims-only diagnostic) rather than guess.
  - Claude read logs before theorising. One CloudWatch read turned a vague
    "500 from runtime" into an exact cause: model access.
  - The model swap was designed for the swap back. "Use Nova for now" was
    implemented as "the model is configuration", enforced by a lint rule
    and recorded in an ADR.
  - When the developer redirected mid-task (ConverseStream), Claude folded
    the change in and updated the IAM permissions and docs to match.
  - When its own design caused a failure (stale stack parameters), Claude
    said so, confirmed it from the deployed stack, and fixed the design
    rather than working around it in the pipeline.
  - Claude was explicit about what it couldn't verify: CloudTrail and model
    availability were outside its permissions, and pushing needed the
    developer's credentials.
