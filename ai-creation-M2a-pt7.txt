CLAUDE:
1. Storing a Game. decide() works on a whole Game. PLAN §4 proposed
   splitting it across many DynamoDB items, with Answers as separate
   write-once items plus atomic counters, so that 50 simultaneous Answers
   never collide. Two options:
     (a) One item per Game, written with optimistic locking and retried on
         conflict. It maps one-to-one onto decide(). A Game is about 50 KB,
         well under DynamoDB's 400 KB limit. At 50 Players, conflicts cost
         a handful of retries.
     (b) PLAN §4's split items. Fewer conflicts, but some rules get
         enforced twice, once in the domain and once in DynamoDB
         conditions.
   My recommendation is (a), with a retry cap and a conflict metric. It
   departs from PLAN §4, so I'd record it in ADR 0006.
2. Testing without Docker: handlers against an in-memory repository; the
   DynamoDB repository against the real dev table.
3. Splitting M2 into four parts:
     M2a the API core, M2b the API stack plus an API-only smoke test,
     M2c the web screens, M2d History.

yes, go with (a), that testing approach and the split

2. S3: A REPOSITORY CONTRACT RUN AGAINST REAL DYNAMODB
------------------------------------------------------------------------------

[Claude built the contract one behaviour at a time, red then green:]
    - a created Game reads back at version 1
    - optimistic locking: saving against the version read bumps it, and a
      stale save throws ConflictError
    - unknown Games return null, and a Game ID can't be created twice
    - Join Code claims: one Game at a time, freed on release
    - one active Game per Host, released only by that same Game, so a late
      release can't wipe a newer claim
    - Quizzes stored per Host, so one Host can't read another's

[One test passed on its first run, because Claude had written the
 duplicate check one slice early. Claude said so, then deliberately
 removed the check to prove the test could fail.]

[Claude wrote DynamoRepository using the single-table key layout, and ran
 the same contract against the real quizapp-dev table in the quizdash
 account. All 6 behaviours passed against real DynamoDB, so the in-memory
 fake used by every other test is faithful.]

3. S1: THE GAME SERVICE, AND A HANG THE TESTS EXPOSED
------------------------------------------------------------------------------

[Slices, each red then green:]
    - createGame from the Host's Ready Quiz, claiming a Join Code and the
      Host's active-Game slot
    - another Host's Quiz, or a Draft, is refused
    - a second Game is refused, without leaving a Join Code claimed by no
      Game (the fix: claim the active-Game slot first)
    - a colliding Join Code is retried
    - THE HANG: the next test, where every Join Code collides, didn't fail.
      It hung. The retry loop was unbounded, and because it only awaited
      microtasks it even starved vitest's own timeout. Only the outer kill
      stopped it. Claude capped the retries (JOIN_CODE_UNAVAILABLE),
      releasing the Host's claim when it gives up.
    - joinGame returns a Player token, and tells the Host on the host
      channel inside PLAN §6's event envelope
    - two Players joining at the same moment both get in. The test runs
      both at once, so one save genuinely loses the race (a real
      ConflictError), and the service reloads and decides again.
    - endless conflicts give up with TOO_MANY_CONFLICTS and publish nothing
      (verified by deliberately breaking the cap)
    - hostCommand checks ownership on every retry
    - submitAnswer: when the last Answer triggers Reveal, the per-Option
      counts go only to the host channel
    - a Game that finishes frees its Join Code and the Host's slot
    - Player snapshots never include the correct Option before Reveal; they
      show my points and rank during Reveal, "removed" for removed Players,
      and the Leaderboard once Finished
    - Host snapshots: the owner only; an answered count during a Question;
      per-Option counts only from Reveal
    - activeGame, so any of the Host's devices can resume

[To keep snapshots identical to what the live events showed, Claude
 extracted revealResults(), leaderboard(), answeredCount() and
 optionCounts() into the domain, rather than duplicating logic. M1's 54
 tests confirmed the refactor changed nothing.]

4. S2: THE HTTP LAYER, AND THE AWS ADAPTERS
------------------------------------------------------------------------------

[Router slices, each red then green:]
    - POST /api/join: 201 with a token, 400 for malformed bodies (via zod
      schemas in the shared contracts package)
    - service errors mapped to status codes: 404, 400, 403, 409, and 503
      for retryable ones
    - Host routes need the Cognito identity (401 without it)
    - a full Host journey: resume, start, a 403 for an intruder, inspect,
      remove a Player, and 409s for the wrong timing or phase
    - Player routes need a bearer Player token (401 otherwise), then serve
      the snapshot and accept Answers

[The AWS adapters: the Lambda handler with real dependencies (48-hour
 Player tokens, cryptographically random Join Codes); an IAM-signed AppSync
 publisher (five events per request, order kept); and Host support in the
 real-time authoriser (Cognito-verified, own Games only, never publish),
 extended test-first from Spike B's tests.]

[A bug caught before deploying: the pipeline still redeploys the Spike B
 stack, which shares the authoriser bundle but has no Cognito settings.
 The new handler would have failed every request there, including
 Players'. Claude made the Host dependencies load only when a Host token
 actually arrives.]

CLAUDE:
M2a, the API core, is done. It's all built test-first. The API package has
59 tests, and 123 pass repo-wide, along with format, lint and typecheck.
All three Lambdas bundle.
One departure from the plan: all the HTTP routes run in one Lambda with an
internal router, instead of one function per route group. It's simpler to
deploy, and can be split later without code changes. I'll note it in the
plan.

Observations worth blogging about:
  - Claude challenged its own plan (PLAN §4's storage design) once the
    domain model made a simpler option clear, and asked before changing
    it, recording the change in an ADR.
  - The repository fake is verified against real DynamoDB by the same
    contract suite. That's the defence against tests that pass against a
    fake that lies.
  - A test exposed a real hang (an unbounded retry loop) before it could
    ever reach production.
  - The concurrency test is real, not mocked: two simultaneous joins
    genuinely race, and the losing write genuinely retries.
  - Claude checked how new code would affect infrastructure that was
    already deployed (the Spike B stack) before pushing.
