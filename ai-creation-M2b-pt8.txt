2. SMOKE RUN 1: THE AUTHORISER CRASHED ON EVERY CONNECTION
------------------------------------------------------------------------------

USER:
pipeline is green, run the smoke test

[Claude ran the smoke test against dev. Sign-in, seeding, the HTTP API
 with its JWT authoriser, and creating a Game all worked. Then the first
 WebSocket timed out waiting for "connection_ack".]
[Claude read the authoriser Lambda's CloudWatch logs and found:
   TypeError: Cannot read properties of undefined (reading 'replace')
     at normaliseChannel ]

CLAUDE:
I found the bug, and it's mine. On a connect, AppSync omits the channel
field entirely rather than sending null, as I'd assumed from the docs. In
my M2a rewrite of the authoriser, I moved the channel normalising ahead of
the connect check, so undefined.replace threw. Every connection then
failed, Players' included. Spike B's version checked the operation first,
which is why its live checks passed.

[Fixed test-first. A new unit test uses AppSync's real request shape, with
 no channel field. It failed with the same TypeError, then passed after the
 fix.]
[Claude also improved the smoke test's WebSocket client to report
 connection errors and closed sockets, instead of timing out silently.]
[Committed 919aff5; the developer pushed.]

3. SMOKE RUN 2: EVENTS THAT SOMETIMES DON'T ARRIVE
------------------------------------------------------------------------------

USER:
pipeline is green, run the smoke test

[Connections and subscriptions now worked, and the Host received its
 events. But the bots timed out waiting for QUESTION_OPENED.]

[Claude investigated step by step rather than guessing:
   1. Lambda logs: no errors in the API or the authoriser.
   2. A hand-made, IAM-signed publish: HTTP 200, nothing under "failed".
      So publishing worked. (Two attempts to run the probe failed on
      module resolution; Claude moved it into the package that had the
      signing libraries.)
   3. Diagnostics: the smoke test now prints every event each client
      received when it fails. The next run passed Question 1 completely,
      then showed all three bots missing QUESTION_REVEALED@v12, while the
      Host's subscription to the very same channel received it.
   4. The authoriser's logs: it ran 9 times (connects and subscribes),
      never during delivery, and wasn't throttled. So authorisation wasn't
      the cause.
   5. An isolated probe: 3 subscribers x 20 events, all delivered, both
      with and without a pause after subscribing. So it wasn't timing
      after subscribing either.
   6. Documentation: AppSync Events is documented as at-most-once,
      best-effort delivery. Occasional loss is expected behaviour.]

CLAUDE:
The design already allows for this. PLAN §2 says events are
notifications, and that the snapshot is the source of truth. My smoke test
was what assumed perfect delivery.
So I'll make the smoke test behave the way real clients must. When an
expected event doesn't arrive within a few seconds, it falls back to the
snapshot endpoint and checks the state from there. It also counts lost
events, so we can see how often it happens.

[Claude rewrote the smoke test's checks on that basis, removed the
 temporary probe and its dependency, and ran the smoke test twice:]

  • Question 1: opened, answered, revealed
  • Question 2: opened, answered, revealed
  • Game finished: 1. Alice 1991, 2. Cara 1976, 3. Bob 0
  • real-time events lost and recovered from snapshots: 0 of 15
  SMOKE TEST PASSED          (and again on the second run)

[Claude recorded the rule in ADR 0002. Every client must re-fetch its
 snapshot on load, on reconnect, when an event's version skips a number,
 and when an expected event is overdue. This becomes a requirement for the
 M2c screens.]

Lesson for the blog: the smoke test did its job twice in one afternoon.
First it caught a real code bug that unit tests built on a guessed request
shape couldn't see. Then it surfaced a property of a managed service that
changes how the UI must be built. Claude separated the two systematically
(logs, a hand-made probe, an isolated experiment, then the docs) before
changing anything, and fixed the test's assumption rather than hiding the
loss.

Observations worth blogging about:
  - Real-environment tests catch what unit tests can't: a request shape
    the docs described one way and the service sent another.
  - When results were confusing, Claude collected evidence before forming
    a theory: logs, then a hand-made publish, then per-client diagnostics,
    then an isolated experiment, then the documentation.
  - The fix matched the platform rather than fighting it: at-most-once
    delivery is handled by the snapshot-first design that was already in
    the plan.
  - Claude removed temporary diagnostic code and dependencies once they
    had served their purpose.
