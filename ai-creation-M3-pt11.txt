------------------------------------------------------------------------------

[Slices, each red then green:]

3. G2: THE GENERATION PIPELINE, WITH THE MODEL FAKED
------------------------------------------------------------------------------

[The model sits behind a two-operation interface (generate candidates,
 verify one), so the pipeline is tested without Bedrock:]
    - verified Questions come back with Options labelled a-d
    - failures are dropped and replaced, and the replacement round asks
      for just the shortfall while avoiding everything seen so far
    - it stops after two replacement rounds, returning what passed
    - nothing passing means GENERATION_FAILED; a refusal means
      TOPIC_REFUSED
    - code validation drops malformed Questions before spending a
      verification call on them (wrong Option counts, duplicate or empty
      Options, an out-of-range answer, empty or over-long text)
    - repeats of the Host's earlier Questions, or of each other, are
      dropped, ignoring case, spacing and punctuation

[Before writing the real adapter, Claude read the installed Strands SDK's
 type definitions. They showed that structured output can be passed per
 call, and which stop reasons mean refusal or content filtering. The
 adapter uses a question writer that can explicitly decline a Topic (a
 schema field) and a sceptical fact-checker, both through the shared
 Converse-only model module (ADR 0005).]

[The agent's HTTP endpoint changed from Spike A's "answer a prompt" to the
 generation contract (generate, or regenerate one Question). Its request
 and response schemas went in the shared contracts package.]

[Claude tried one real 3-Question generation from the laptop, to catch
 prompt or schema problems early. The deploying IAM user isn't allowed to
 call Bedrock, so it couldn't run. Claude reported that as an open risk:

4. G3: THE API
------------------------------------------------------------------------------

[Repository contract, in memory AND on real DynamoDB:]
    - Quizzes gain optimistic locking, because the worker writing a Draft
      can race the Host editing it
    - deleting a Quiz
    - the daily limit as an atomic increment-if-below-the-limit: four
      requests fired at once against a limit of three, and exactly three
      got through
[Quiz service, red then green:]
    - creating a Quiz validates, counts against the limit, stores it as
      generating, and hands off to a background job
    - the limit resets at midnight in Sydney. The test checks that 12:30
      and 13:30 UTC on 25 October fall on different Sydney days.
    - the worker's job turns the Quiz into a Draft with fresh Question
      IDs, and passes the agent the Host's earlier Questions on similar
      Topics only
    - a refusal marks the Quiz Failed (TOPIC_REFUSED); an agent crash marks
      it Failed (GENERATION_FAILED) rather than leaving it generating
      forever
    - review operations, listing every status, deleting, all limited to
      the Quiz's own Host
    - regenerating one Question counts against the limit only once the
      request is known to be valid, and avoids the Draft's other Questions
[Routes: 202 for background work, 429 over the limit, 400 for bad input,

Observations worth blogging about:
  - The AI part was designed so most of it can be tested without AI:
    generate and verify are a two-operation interface, so the
    orchestration, validation and de-duplication are covered by fast
    tests.
  - The model's output isn't trusted just because it parsed: code checks
    every Question's shape before spending a verification call on it.
  - Cost and fairness were designed in, not bolted on: an atomic daily
    limit that can't be beaten by simultaneous requests, no automatic
    retries that could charge twice, and the limit counted only after a
    request is known to be valid.
  - Claude used its own safety checks on edits, so a mismatched edit
    stopped instead of silently corrupting a file. When one unchecked edit
    did slip through, the failing tests caught it at once.
  - Claude stated plainly what it couldn't verify locally (the real model
    call) instead of claiming the feature worked.
